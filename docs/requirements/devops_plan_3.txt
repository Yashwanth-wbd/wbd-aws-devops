## 0. Role, objective, and golden rules

**You are a senior AWS DevOps engineer.** Change the built v2 WBD MMM platform to the v3 architecture.
The application (UI + API) runs on **Amazon ECS on Fargate**; optimization and model training run on
**Amazon SageMaker**, orchestrated by **AWS Step Functions**; optimization requests are **buffered in
Amazon SQS** and dispatched by a **Lambda**; data engineering runs on **Databricks on AWS** with
**Delta Lake on S3**; planners sign in with **WBD Okta**.

**Golden rules (apply to every step):**
1. **Everything is Terraform**, run from GitHub Actions via OIDC. Exceptions: the one-time state bootstrap and the first apply per account — run with SSO.
    80|2. **No secrets in Git, images or Terraform variables.** Runtime secrets live in Secrets Manager / SSM. (v3: the ALB needs the Okta OIDC client secret in its listener configuration – Terraform reads it from Secrets Manager, so it is only in the encrypted state file [ASK].)
3. **Modularize**: reusable modules in `infra/modules/`, thin stacks in `infra/environments/{dev,staging,prod}/`; edit dev, then `scripts/sync-environments.ps1`.
4. **Build order: dev → prove it works → staging (same code) → prod (same code).**
5. **Validate after every step.**
6. **Naming:** `mmm-<env>-<component>` (env = `dev|stg|prd`). **Tags:** `Application, Environment, Owner, BusinessUnit, DataClassification, ManagedBy, Component`.
7. **SageMaker jobs, Lambda functions and ECS tasks run inside the VPC** (private subnets, no public IP), with KMS on volumes, queues and outputs.
8. **Remove what v3 drops** (Cognito, Aurora) – no leftover modules, variables, outputs, docs or runbooks.

### Step 9 — Optimization engine (SQS + dispatcher Lambda + Step Functions + SageMaker + publisher) (v3)
- **sqs** `mmm-<env>-optimization-requests` (**Standard** queue [ASM] – duplicates are harmless because the execution name is the `run_id`): SSE-KMS (`sqs` key), visibility timeout 6 × dispatcher timeout, retention 4 days, long polling, queue policy = API task role send + dispatcher consume + TLS-only; **DLQ** `…-dlq` with `maxReceiveCount = 10` [ASM], retention 14 days.
- **Message contract (API → queue):** `{"run_id", "business_unit", "input_s3_uri", "requested_by", "dry_run": false}`. The API writes the run row with status `QUEUED` before sending.
- **lambda-function** `mmm-<env>-run-dispatcher` (DevOps-owned code in `modules/run-dispatcher` [ASM], no business logic, no DB access): SQS event source mapping (batch size 10, **maximum concurrency 2**, `ReportBatchItemFailures`); per batch it reads `max_concurrent_runs` from SSM, counts RUNNING executions of the optimization state machine, and for each message either calls `StartExecution` (name = `run_id`; `ExecutionAlreadyExists` = success) or returns it as a batch-item failure so SQS re-delivers it after the visibility timeout. Role: `sqs:ReceiveMessage/DeleteMessage/GetQueueAttributes`, `states:StartExecution` + `ListExecutions` on the optimization state machine, `ssm:GetParameter`, `cloudwatch:PutMetricData` (namespace `MMM/Optimization`), KMS decrypt; in the VPC (private-app, `lambda` SG); logs (KMS, retention); reserved concurrency 2.
- **Alternative [ASK]:** EventBridge Pipes (SQS → Step Functions) instead of the Lambda – no code, but no concurrency gate; the slide shows a Lambda, so Lambda is the default.
- **step-functions** `mmm-<env>-optimization`: unchanged definition (ApplyDefaults → GetOptimizerImage → RunOptimizer `createProcessingJob.sync` → PublishResult / PublishFailure); now started by the dispatcher instead of the API.
- **sagemaker** run role, **results-publisher** Lambda (`live` alias, sync invoke with retries, no DLQ), SSM image pointers: unchanged; the publisher writes to **RDS PostgreSQL** through RDS Proxy.
   240|- **Cancel:** the API marks a queued run `CANCELLED`; once the run has started, the API calls `StopExecution` (the dispatcher has no DB access, so a cancelled run may still start and is then stopped) [ASM].
- **Queue wait limit:** the dispatcher deletes messages older than `max_queue_wait_minutes` (default 30 [ASM]) without starting them and publishes metric `ExpiredRunRequests` (alarm > 0); the API shows "timed out in queue" for runs still `QUEUED` after that time [ASK].
- **Validate:** 20 messages with `max_concurrent_runs = 5` → never more than 5 RUNNING executions, all 20 finish; the same `run_id` twice → one execution; a malformed message lands in the DLQ and alarms; the publisher writes the run to RDS; a failed job marks the run failed and alerts.
