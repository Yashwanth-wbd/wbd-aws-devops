## 0. Role, objective, and golden rules

**You are a senior AWS DevOps engineer.** Change the built v4 WBD MMM platform to the v5 architecture.
The application (UI + API) and the inference & optimization engine run on **Amazon ECS on Fargate**;
model training, evaluation and the registry stay on **Amazon SageMaker**; everything is orchestrated by
**AWS Step Functions**; optimization requests are **buffered in Amazon SQS**; data engineering runs on
**AWS Glue** with **Delta Lake on S3** and **lineage in the Glue Data Catalog + SageMaker**, fed by an
export from the WBD Databricks source catalog; **all writes to RDS go through the API or the results/data
publisher**; planners sign in with **WBD Okta**.

**Golden rules (apply to every step):**
1. **Everything is Terraform**, run from GitHub Actions via OIDC. Exceptions: the one-time state bootstrap and the first apply per account — run with SSO.
2. **No secrets in Git, images or Terraform variables.** Runtime secrets live in Secrets Manager / SSM (v5 removes `rds/etl`). Values supplied by WBD are marked `# add actual value`.
3. **Modularize**: reusable modules in `infra/modules/`, thin stacks in `infra/environments/{dev,staging,prod}/`; edit dev, then `scripts/sync-environments.ps1`.
4. **Build order: dev → prove it works → staging (same code) → prod (same code).**
5. **Validate after every step.**
6. **Naming:** `mmm-<env>-<component>` (env = `dev|stg|prd`). **Tags:** `Application, Environment, Owner, BusinessUnit, DataClassification, ManagedBy, Component`.
7. **ECS tasks, Glue jobs, SageMaker jobs and Lambda functions run inside the VPC** (private subnets, no public IP), with KMS on every store (v5 draws KMS on each one).
8. **One IAM role per integration** (v5 draws "AWS IAM" on every arrow), all with the permission boundary.
9. **Remove what v5 drops** (`rds/etl`, `mmm_etl`, Glue DB path) – no leftover variables, outputs, docs or runbooks.

Role adds `sagemaker:CreateContext`, `CreateArtifact`, `AddAssociation`, `AddTags` (+ Describe / List) on `mmm-<env>-*` lineage entities.

- **Validate:** a refresh writes `rds-export/<bu>/<refresh_id>/`, the publisher loads it into RDS, SageMaker trains / evaluates / registers, `RecordLineage` creates the context + associations (`aws sagemaker query-lineage` from the model package reaches the training data and the export), model results appear in RDS; Glue has no network path to RDS.

## 12. Order-of-operations summary

**Glue module (no JDBC, no rds-db:connect) + network (Glue out of data-clients) → secrets (remove rds/etl,
proxy auth) → lakehouse `rds-export/` lifecycle + db-bootstrap without mmm_etl → publisher role / timeout for
`reference_data` → model-refresh states `ExportReferenceData` → `PublishReferenceData`, `RecordLineage` +
role lineage APIs → monitoring (dashboard, optional CloudTrail data events) → docs / runbooks / data README /
mock-plan → staging → prod → 🚦 RELEASE 1 (GenAI off) → Release 2 GenAI → handover.** One step at a time;
validate each; keep all three environments on identical code.
